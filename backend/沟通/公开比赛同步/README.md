# 公开比赛同步（沟通/公开比赛同步）

**方向**：美国 → 北京

把美国比赛库里已公开的比赛、届次推到北京的公开副本，小程序首页和详情从北京读。

**怎么同步**：比赛有改动时推，只推有变化的；按大小分批；下架的在北京也删；每天整体核对一次；美国读到 0 条时拒绝推送（防止把北京清空）。

| 文件 | 跑在哪 | 做什么 | 要搬过来的 |
|---|---|---|---|
| 美国端.mjs | 美国服务器（定时器每 5 分钟） | 推送：读比赛库里已公开的比赛和届次，按白名单整理，只推有变化的；海报先推（一张一个请求，推过的不再推）；每 24 小时整体重推一次；读到 0 条不推；下架的在北京也删 | 美国 sync-public-cache.mjs |
| 北京端.mjs | 北京服务器（只听本机，nginx 把 /sync/public 转进来） | 接收：验签名和时间，交给北京主数据库的 同步.收下（版本号更大才覆盖、下架的删掉、海报先存），整批不对整批不收 | 上海云函数 publicSync |
| 格式.mjs | 两边共用 | 公开字段白名单（照旧 toPublicCache，字段名用美国比赛库的）；签名规则 | adminData/publicCache.js |

- **秘钥**：`SYNC_SECRET`，两台共用，和登录令牌的密钥分开。每个请求带 `x-sync-time`、`x-sync-signature`（HMAC-SHA256(时间.正文)），北京只认 5 分钟以内的，抓到的旧请求不能重放。
- **公开字段**：照旧 toPublicCache；不公开状态理由、人工改过的字段、发现途径、AI 核对过程、legacy、候选海报、谁建的谁改的。已归档的带上下一届预计（旧记录带过来的，在 legacy 里）。
- **信息来源**（2026-11-12 用户定，和北京约定的字段名）：届次的 `data.info_source` 是 `official` 或 `school_repost`（高校转发），`school_repost` 时另带 `data.info_source_url`（转发页网址）。
  美国比赛库不另存这个字段，`整理届次` 从来源推：有官方、核验有效的 http(s) 来源 → `official`；没有、但有核验有效的高校转发来源（`source_type: school_repost`）→ `school_repost`，
  网址取核对时间最新的；都没有（旧数据）→ `official`。所以美国端读的是全部核验有效的来源（不只官方的），`data.sources` 仍只给官方的。
  这样以后新维护找到官方通知、补上官方来源，下次推送自动变回 `official`，不用另改字段。上线后第一次推送每个届次的内容都多了这个字段，会全部重推一遍。
  北京主数据库接收、公开数据详情交给小程序（`infoSource`、`infoSourceUrl`）由北京那边做。
- **现在的状态**：能用，有测试（两边都用内存库，网络换成直接调北京端）。还没部署。
- **规矩**：两端放在同一个文件夹里，格式和密钥规则只定一次；只经 `共用/db/index.mjs`、`美国/db/index.mjs`、`北京/主数据库/index.mjs`、`北京/副数据库/index.mjs` 读写数据库；只走服务器之间，不经过小程序。
