## 什么时候跑（2026-11-01 用户定）

定时器每天 9:00–18:00 每 5 分钟启动一次（见 `../../定时/`），**每次维护一个比赛**，依次进行（`轮流.mjs`）：

- 挑哪个：从没维护过的排最前（同样按编号），再按上次维护时间从早到晚；7 天内维护过的、已删除的跳过；都在 7 天内维护过就什么都不做。
- 做完在比赛上记下 `last_maintained_at`，留一条操作日志（“维护比赛”，含失败的检查）。检查出错也照样标“维护过”，7 天后轮到再查。试跑不记。
- 不叠着跑：上一次还没完（`日志/.维护中.lock`，超过 1 小时算异常留下的）就跳过；每晚流程还在跑（`PIPELINE_LOG_DIR/.运行中.lock`）也跳过这一轮（`运行锁.mjs`）。
- 现在库里 376 个比赛，每天约 108 个，三天半轮完一遍。
- 命令行：默认维护下一个；`--比赛 编号` 指定一个；`--全部` 全部一起跑（手动用）；`--dry-run` 试跑。

## 一次运行的过程

1. **审计**：5 项检查同时跑，每项限时，只读比赛库，交回发现的问题。一项失败不影响别的。
2. **分流**（`处理/分流.mjs`）：
   - 错误、给了正确值、有把握 → 机器直接改；
   - 错误、给了正确值、但不确定 → 转人工；
   - 缺失的，或知道错了但不知道正确值的（比如链接打不开）→ 调工具查找；
   - 查到了、有把握、带原文出处 → 直接补上；查到了但拿不准或没出处 → 转人工；没查到 → 留着，下次审计还会发现、再查；
   - **人工改过的字段**（`manual_fields`）机器不自动改，一律转人工。
3. **组装**（`处理/组装.mjs`）：
   - 改正：写在问题所在的记录上；改“状态”时顺带记状态时间；每处改正在后台记录里留一条操作日志（原值、新值、依据、出处、哪项检查）。
   - 转人工：不另建表，直接在届次上标记：状态改成“待人工审核”，理由（`status_reason`）加一条。格式是“[维护·检查项] 字段：依据（建议：…；出处：…）”。比赛级字段的问题标在这场比赛最新的一届上。同一检查项、同一字段已有理由的不重复加。后台按状态筛出来。
   - 同一条记录的几处改动合成一次修改，带读到的版本号。
4. **提交**（`提交.mjs`）：一个事务写进比赛库；期间被人改过的（版本号对不上）跳过不覆盖。

已删除的比赛和届次比赛库默认读不到，维护碰不到它们。

## 问题的写法

检查项交回 `{ problems: [问题] }`，每个问题：

| 键 | 意思 |
|---|---|
| table、key | 哪张表（competition 或 edition）、哪条记录 |
| 字段 | 哪个字段 |
| 类型 | 错误 或 缺失 |
| 现在的值 | 库里现在是什么（操作日志里记为原值） |
| 建议改动 | 知道正确值时给出，如 `{ registration_end: '2026-09-10' }`；不知道就不给 |
| 把握 | 有把握 或 不确定 |
| 依据 | 为什么认为有问题 |
| 出处 | `[{ 网址, 原文 }]` |

查找交回 `{ 找到, 改动, 出处, 把握, 说明 }`；值必须能在原文里逐字找到出处才算找到。

## 怎么运行

```bash
node backend/美国/db/维护/run.mjs                 # 全部检查跑一遍，处理结果写进比赛库
node backend/美国/db/维护/run.mjs --dry-run       # 试跑：照常审计和分流，不写比赛库
node backend/美国/db/维护/run.mjs --only 状态      # 只跑某几项检查
```
