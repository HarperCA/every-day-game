# 每晚总流程（pipeline）

寻找新比赛的流程。每晚只有启动这一步按时间触发，后面全部由代码按顺序驱动：上一个模块跑完、结果检查通过，下一个模块才开始；模块内部并发调用外部接口。
库里已有记录的维护（追溯、监测、复检、归档、已发布比赛的核验）不在这里，在 `../维护/`，两边只通过比赛库来往。

6 个模块：搜索 → 对比去重 → 筛选（标题筛选、Jev 筛选、Codex 代理追踪）→ 读详情和抽取 → 审核 → 入库 →（06 的写入主库写进比赛库，写进去就是发布）。2026-11-01 通知追溯并进筛选，验收去掉。
先和库里对比去重，库里已有的不再往下走；审核放在入库之前，过了才入库；验收在写进比赛库之后跑。
整条流程跑完后，才把当晚可以入库的改动统一写进总库。

## 怎么运行

```bash
node backend/美国/pipeline/run.mjs              # 正式运行（骨架阶段总库是假的）
node backend/美国/pipeline/run.mjs --dry-run    # 试跑：最后不写总库
node backend/美国/pipeline/run.mjs --run 2026-10-29 --from 04   # 接着某一晚，从第 4 个模块重跑
npx vitest run backend/美国/pipeline            # 跑测试
```

## 一晚的过程

1. **加锁**：日志目录里放一个锁文件，同一时间只能跑一次；超过 12 小时没解锁的视为上次异常退出留下的。
2. **建运行文件夹**：按北京时间的日期命名，同一天再跑依次加 `-02`、`-03`；顺手删掉超过 90 天的旧文件夹。
3. **依次运行模块**：
   - 把当晚还“进行中”的条目交给模块（已丢弃、顺延、失败的不再交出去）；
   - 模块在时间上限内运行，超时会触发停止信号；
   - 交回的结果先过交接检查，合格才用一个事务写进 run.db；
   - 关键模块失败，整晚停下、不提交；非关键模块失败，记为“跳过”，继续跑后面的。
4. **提交**：把 run.db 里可以入库的改动用一个事务写进总库（试跑不写）。
5. **写报告**：report.md 列出每个模块的结果、条目去向、提交结果、没写进总库的改动和原因。


- `日志/` 写在 `.gitignore` 里，不提交，不推送。

## run.db 里有什么

| 表 | 存什么 |
|---|---|
| items | 每条候选或记录：编号、类型、状态（进行中、已丢弃、顺延、失败）、最后经过的模块、全部字段 |
| trail | 每条在每个模块里的结果和原因，并记下改之前的样子，用于从中间重跑时恢复 |
| blobs | 网页正文等大块内容，按内容指纹只存一份 |
| changes | 待写进总库的改动，以及最后提交的结果（已写入、跳过、不提交）和原因 |
| modules | 每个模块的状态、统计、错误 |
| calls | 每次外部接口调用的记账 |

## 模块的写法

```js
export async function run(input, ctx) {
  // input.items：当晚还在进行中的条目
  // 返回：
  return {
    items: [{ key, kind, status, data, result, reason }],   // 这一步处理过的条目
    changes: [{ table, key, op, payload, baseVersion, itemKey }],  // 想写进总库的改动
    problems: [],                                            // 模块级的问题
  };
}
```

规矩：只开 `run` 一个入口；不 import 别的模块；不直接写数据库；不悄悄丢掉条目。依赖方向由测试 `test/单独/imports.test.mjs` 检查。

## 提交到总库的条件

一条改动同时满足才写：所属条目还在“进行中”；通过入库规则检查；修改时总库这一行的版本号和模块读取时一样（不一样说明流程开始后有人改过，跳过不覆盖）。事务中途出错就整个撤回。
