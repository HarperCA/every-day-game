## 流程里这一步（入库总管）

逐条做（同一次两条指向同一个比赛时，第二条能看到第一条已经决定新建）：

1. **对照主库**：名称或别名规范化后一样就是已有比赛；条目带了 `比赛编号` 的只在这个比赛下认届次，带了 `届次编号` 的直接用这一届（见下面“给新维护用的选项”）。
   - 认届次：年份一样、或第几届一样就是同一届。比较前规范化（2026-11-08 代码审查，以前字符串完全相等，“第10届”对不上“第十届”就重复建届）：
     年份区间取前一个年份（“2025—2026”和“2025”算同一年），第几届中文、阿拉伯数字互认（第十届 = 第10届）。
   - 没有：新比赛；同一次前面一条已经决定新建的，算它的新一届。
   - 有，但没有这一届（年份或第几届不同）：新一届，顺序接着排；比它早、已发布的届次一起归档（待人工审核的不跟着归档）。
   - 有这一届：有新来源就只补来源；来源都有了就是“已处理过”，标已丢弃。
   - 同一次前面一条刚决定新建的同一届（年份或第几届一样）：算补来源，不再建第二次（2026-11-08，中车杯同一届建了两次）；
     同一次补进同一届的来源编号接着排，同一网址不再补。
2. **整理字段**（按 `backend/美国/db/描述/`）：
   - 名称里的年份、第几届拆到届次的年份、届次两栏，原文留在届次名称。
   - 编号沿用现有格式：比赛 `event-` 加规范名称算出的 8 位短码（同名同号），届次 `edition-比赛码-年份`（没有年份用 `n顺序`），来源 `source-届次码-序号`。
   - 级别先填“其他/未明确”（抽取里没有，不靠主办方名字猜）；专业分类用三项核验判出来的；空的填 null；参赛形式、费用分档这些没填的由比赛库补默认值。
   - 来源是 05 核验过的官方来源。
3. **发布门槛**（`美国/程序审核`）：没过的不入库，标已丢弃，原因写“06 入库·发布门槛：……”。
4. 报名已截止的为**已归档**，其余为**已发布**；放进小数据库的待写入。

条目的 `data.ingest`：`{ decision: 新比赛 / 新一届 / 补来源 / 已处理过, competitionId, editionId, status?, 改动: [{ 届次, 字段, 改前, 改后 }] }`。

## 给新维护用的选项（2026-11-08，每晚流程不带，行为不变）

由 `总控/入库指定网址.mjs` 带进来。用户定：“维护主要是维护已经有的比赛，读全文看看现在写的是否正确，不正确就进行更改”。

- **条目 data 带 `比赛编号`**：只在这个比赛下认届次。对上已有届次走补来源 / 已处理过；新的一届建在这个比赛下；绝不按名字另建比赛（名字写法不同时会另建，比如“中联杯”）。主库里没有这个比赛（不存在或已删除）就报错，这条标失败。
- **条目 data 带 `届次编号`**（2026-11-08）：直接用这一届，不按名字认——有新来源补来源，没有就是已处理过；开了更新已有就比字段。这一届主库里没有（不存在或已删除）、或不属于条目的 `比赛编号`，这条标失败，原因写“06 入库·出错：指定的届次 …… 主库里没有 / 不属于比赛 ……”。
- **input 带 `更新已有: true`**：对上**库里已有的一届**（补来源、已处理过）时，用这条通知整理出的届次内容和库里那一届逐项比（`整理字段/比对届次.mjs`）：
  - **2026-11-09 用户定“只改确定的事实”**（美国试跑把 event-cmp002 的赛制改成只剩“（一）主体赛事”、参赛资格改窄；本地实测报名截止从“12-04 23:59”变成“12-04”、主办方改成“参赛指南”）。字段分两类：
    - **确定事实，不同就改**：`registration_start`（报名开始）、`registration_end`（报名截止）、`competition_start`（比赛开始）、`competition_end`（比赛结束）、`registration_url`（报名网址）、`fees`（费用原文）。新值非空、规范化以后和旧值不同就改。
      `competition_start`、`competition_end` 现在 04 不抽、届次内容不交，实际不会比到，以后交了就按这条规则。`fee_type`（费用分档）现在的抽取不交，不比。
    - **其余只补空**：`format_and_rules`（赛制和规则）、`participants`（参赛对象）、`eligibility`（参赛资格）、`registration_method`（报名方式）、`organizer`（主办方）、`team_size`（团队人数）、`reward_highlights`（奖励亮点）、`pending_announcement`（待公布），以及 `edition_year`、`edition_ordinal`（认届次用的，改了下次就认不出这一届，2026-11-08 起就是这样）。
      只在库里原来是空（null、空串、只有空白、空列表）时补上，原来有值就不动。主办方届次没填、比赛有主办方的算不空，不补。`pending_announcement` 库里总有 true/false，实际不会补；而且只有记录里明确写了才比（现在的抽取不交这一项）。
  - **日期规则**（四个日期字段）：先按北京时间换算；`2026-12-04`、`2026年12月4日` 和北京时间当天零点算同一个。
    - 不同日期 → 改（旧值带时间也改）。
    - 同一天、新值只有日期、旧值带具体时间（旧 `2026-12-04T23:59:00+08:00`、新 `2026-12-04`）→ **不改**，不把精确时间改粗。
    - 同一天、新值带时间、旧值只有日期 → 改（变精确）；同一天两个不同时间 → 改。
  - 不比：编号、所属比赛、顺序、届次全称（各通知标题写法不同，会来回改）、状态和状态理由、版本和时间、发现经过、级别、分档类字段、海报、推荐、manual_fields 本身。
  - 规范化：文字去首尾空白、连续空白算一个；年份连接号统一；网址按网址键比（不分 http/https、www、结尾斜杠）；回报列表不看顺序。新值空不覆盖已有值。
  - 报名网址就是这条通知自己的网址时不拿来改（多半是抽取没抽到、拿通知网址顶上的）。
  - 人工改过的字段（manual_fields）照上面同样的规则（确定事实照改、其余只补空），不做特殊标记。
  - 每晚流程不开 `更新已有`，对上已有届次时不比字段，所以这套规则只管维护。
  - 照样补来源。改动是一条带读到的版本号的修改（写入时版本对不上就跳过），另加一条后台记录（audit_log，action `入库改届次`，detail：`{ 比赛, 改动: [{ 字段, 改前, 改后 }], 依据网址, 来源们, 来源 }`）。
  - 已处理过的（来源都有了）有改动时放进待写入（进行中），没改动照旧标已丢弃。
  - 同一次几条改同一届，后一条在前一条改过的基础上比，不互相覆盖。同一次刚建的届次不比。
- input 带 `来源`：写进后台记录 detail.来源（没给写“每晚流程”）。
- **input 带 `不审核: true`**（2026-11-08 用户定“进行维护的时候不需要审核”“发现新的一届直接进行调换”）：`入库指定网址` 这时不跑 05，候选没有 `data.review`。
  - 处理哪些：04 抽取过（有 `data.extraction`）、还没入库的候选（带了 05 通过的 review 的照旧用 review）。没开不审核时，没有 review 的照旧不处理。
  - 记录：`common/candidate.mjs` 的 `合成记录(item.data)`，和 05 交给三项核验的那条一样（没有 Kimi 改正；报名网址没抽到时是通知网址）。
    记录里不放 `pending_announcement`，所以对上已有届次时不比这一项；新建届次时报名截止没抽到就写“时间待公布”（和三项核验一样）。
  - 来源：这条通知网址 + 04 补读到的正式通知（`extraction.supplement.noticeUrl`），按网址键去重，按来源表和发布门槛“核验过的官方来源”的要求填齐：
    `source_type: organizer_notice`、`is_official: true`、`validity_status: valid`、`last_verified_at` 写当时；
    `title` 用通知标题（补读的通知用比赛名）、`content_summary` 写“新维护读详情抽取（未经审核）：名称；抽到 哪些字段”、`evidence_excerpt` 用抽取的逐字引文、
    `review_reason` 写“新维护：出自已判断为官网的页面，维护不审核（2026-11-08 用户定）”、`supports_fields` 写 name 和抽到值的字段。
  - 对上已有届次（补来源 / 已处理过）：和上面一样，开了 `更新已有` 就比字段、改字段，照样补来源。
  - 新的一届：**不过发布门槛**，直接新建；报名已截止的为已归档，其余已发布；被它替代的旧届次（比它早、已发布的）照旧归档（“调换”）。原因写“新一届，维护不审核，发布”。
  - 新比赛：维护不新建比赛。带 `比赛编号` 时对照主库本来不会交回新比赛；没带又对不上已有比赛的，标已丢弃，原因“06 入库·对照主库：维护不新建比赛（没对上已有比赛，不审核模式不新建）”。

## 写入主库（给总控调）

`写入主库({ 小数据库, 主库, log, 试跑 })`：

- 只写所属条目还在“进行中”的改动；03、05 记的“拒过的网址”不看条目状态。
- 一条候选的改动一组写：主库按字段规则校验，有一项不合格，这条候选的改动全都不写，候选标已丢弃，原因写“06 入库·写入主库：字段不合格：……”。
- 流程开始后有人改过的行（版本号对不上）跳过，不覆盖；同一组里记这一行的后台记录跟着跳过。
- 出了预料之外的错整个撤回，主库保持原样。
- 每条结果写回小数据库，当晚报告从这里出。试跑不写，只交回能写多少条。
