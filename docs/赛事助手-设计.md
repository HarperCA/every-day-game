# 赛事助手（聊天找比赛）设计

2026-10-16。方向：**服务器做厚，小程序做薄**。理解用户的话、查赛事、组织回答、限额、记录，全在自有服务器；
小程序只负责显示对话和赛事卡片。不依赖微信的 agent 能力（`app.json` 的 `agent.skills`），
因为它走微信的服务端，我们控制不了，也没确认对这个 appid 放不放行。

界面原型（假数据）：https://claude.ai/artifact/RwDk3J2GF2AVaiVKs4LxKj ，蓝白配色，卡片只有名称、报名日期、查看详情、加入提醒。

## 1. 一句话的工作方式

用户说一句话 → 服务器让大模型把它**翻译成筛选条件** → 服务器自己用代码去赛事库里查 →
卡片由代码根据查到的记录生成，大模型只写一句推荐理由。**赛事名、日期、链接永远来自赛事库，不来自大模型。**

## 2. 现成可以直接用的

| 要的东西 | 现成的位置 |
|---|---|
| 筛选能力 | `publicData/publicQuery.js` 的 `filterPublicRecords`，已支持 keyword、registrationStatus、eventLevel、profession、participationFormat、teamSizeCategory、feeType、registrationOrganization、region、lifecycle、registrationWithin；专业关键词会自动对到专业大类 |
| 只展示审核通过的数据 | 同一函数已限定 `data_status`、`system_validation=passed`、`manual_review=passed` |
| 大模型调用 | DeepSeek（`EXTRACT_AI_BASE_URL`，`aiReasoning.js`、`competitionAiReview.js` 里已有 `chat/completions` 的调用写法），Kimi 可作备用 |
| 接口形状 | `apps/server/src/index.mjs` 的 `mount(name, handler, {deriveContext})`，`POST /api/<名字>`；用户侧接口用 `userSessionToken` 认身份（同 `userData`） |
| 用量记账 | `globalThis.__apiUsage`，`mount` 已按“函数.操作”记账 |
| 详情页、提醒 | 小程序 `pages/detail`、`services/reminders.ts` |

## 3. 新增的接口

`POST /api/assistant`，需要登录会话（同 `userData`）。

请求：`{ action:'chat', userSessionToken, message, sessionId? }`

返回：
```json
{
  "ok": true,
  "sessionId": "…",
  "reply": {
    "text": "按 计算机 · 国家级 · 可组队 筛到 2 个：",
    "cards": [{ "id": "…", "name": "…", "regStart": "…", "regEnd": "…" }],
    "options": ["计算机", "机械"],
    "relaxed": ["去掉了“下个月”"],
    "source": "赛事库 · 专业=计算机，级别=国家级"
  }
}
```
`cards` 里只放四样：名称、报名起止、id（供“查看详情”跳转）、是否已加入提醒。

## 4. 一次对话在服务器里怎么走

1. **读取上下文**：取该用户的偏好（专业、年级，`userData` 里已有）和最近 6 轮对话。
2. **第一次调大模型（理解）**：不开思考、要求只输出 JSON：
   `{ intent: search | followup | chitchat | out_of_scope, filters:{…}, ask:"要追问的话"|null, options:[…] }`。
   提示词里写明允许的筛选字段和每个字段的合法取值（取自赛事库真实取值）。
3. **代码校验**：筛选条件逐项对照白名单，不合法的丢掉，不信任大模型的输出。
4. **查赛事库**：调 `filterPublicRecords`。
   - 0 条：按固定顺序放宽（先去掉报名时间，再去掉组队，再去掉级别），每放宽一步记进 `relaxed`，回复里如实说明；仍然 0 条就直说“库里没有”，**不凑数**。
   - 条件不够且结果太多（>8）：先追问一句（`ask` + `options`），不硬猜。
5. **第二次调大模型（措辞）**：把查到的前几条记录交给它，只让它写“一句开场 + 每个卡片一句推荐理由”的 JSON。
   服务器检查：理由里不出现不在记录中的日期和链接；失败就退回模板文案（“按你的条件找到 N 个”）。
6. **拼卡片和回复**，写日志，返回。

两次调用都带 8 秒超时；任何一步失败，退化成“用关键词直接搜”的结果，不让用户看到报错。

## 5. 安全和成本

- **注入防护**：用户的话只放在 user 角色，赛事记录当作数据；回复里的名称、日期、id 只能由代码从记录生成。
- **范围限制**：与找比赛无关的问题（`out_of_scope`）统一礼貌拒绝，不调第二次模型。
- **限额**：每个用户每天 N 条（建议 30），每条消息最长 200 字；超限返回固定提示。N 放在服务器环境变量里，可调。
- **缓存**：相同筛选条件（按条件哈希）的查询结果缓存 5 分钟。
- **模型选择**：沿用 DeepSeek，关掉思考以降低延迟和花费；接口异常时自动切 Kimi。
- **记录**：每次对话写入 `assistant_logs`（原话、解析出的条件、返回的 id、耗时、是否放宽），用于以后在后台查看和改进提示词。会话上下文存 `assistant_sessions`，7 天过期。

## 6. 小程序侧（薄）

- 新增 `pages/assistant`：对话列表、快捷问题、输入框，复用现有 `services/`。
- 新增赛事卡片组件：名称、报名起止、`查看详情`（跳 `pages/detail`）、`加入提醒`（调用 `reminders` 服务）。
- 样式沿用原型的蓝白配色，写进小程序自己的 `wxss` 变量。
- v1 不做流式输出，用“正在输入”动画，预计 2 到 4 秒出结果；以后需要再加 SSE。

## 7. 分步

- **M1 服务器接口**：`assistant` 模块 + 单元测试（条件白名单、放宽顺序、注入和越权、假模型），用 curl 就能验证。
- **M2 小程序页面**：对话页、卡片组件、提醒联动。
- **M3 治理**：限额、日志、后台查看对话和命中率。

## 8. 待定

- 助手入口放在哪（首页顶部、底部栏，还是“我的”页）。
