# 管理后台 CloudBase 配置

管理后台不再把浏览器 `localStorage` 作为主数据库。当前数据流为：

`React 管理后台 → adminData 管理云函数 → CloudBase 云数据库`

浏览器缓存只用于网络异常时保留当前页面数据，云端写入失败会在后台左下角显示错误。

## 已完成

- CloudBase Web SDK 已接入管理后台。
- `adminData` 普通云函数已部署到 `daily-contest-dev-d8dbbhc653e221`。
- 赛事、纠错、AI任务和操作日志均已接入云端读写队列。
- 管理员口令只由云函数环境变量校验，不打包进网页。

## 控制台只需配置一次

1. 在“文档型数据库”创建集合 `admin_state`。
2. `admin_state` 权限选择“无权限（仅管理员/云函数可读写）”。
3. 打开“云函数/托管 → adminData → 函数配置 → 环境变量”。
4. 新增变量名 `ADMIN_TOKEN`，值复制项目根目录 `.admin-token.local` 中等号后的内容。
5. 为 Kimi Code 赛事审核增加云函数环境变量：`AI_PROVIDER=kimi-code`、`AI_BASE_URL=https://api.kimi.com/coding/v1`、`AI_MODEL=kimi-for-coding` 和 `AI_API_KEY`。密钥只能保存在云函数中，值里不要带引号或首尾空格。该接入消耗 Kimi Code 会员额度；若改用产品级开放平台，只需替换这四个环境变量。
   - **环境变量保存后必须重新部署 `adminData` 云函数才会生效**，否则函数仍读到空值并返回 `ai_api_key_not_configured`。
   - 运行时不限版本：Nodejs16 及以下没有全局 `fetch`，`httpClient.js` 会自动退回内置 `https` 实现，不需要重建云函数。
   - 把 `adminData` 的**超时时间调到 60 秒**：一次审核要先抓取最多 3 个来源页面再调用模型，默认 3 秒必然超时。
6. 在“身份认证 → 登录方式”开启“匿名登录”，供网页获取调用云函数所需的临时用户会话；匿名用户不能直接读写管理集合。
7. 在 Web 安全域名中加入后台正式域名。开发期间按 CloudBase 控制台要求配置 localhost/本地调试来源。

完成后，启动后台，在登录页输入同一个 `ADMIN_TOKEN`。首次登录会把30场种子赛事初始化到 `admin_state/competitions`，以后所有修改均写入云端。

登录成功后，长期 `ADMIN_TOKEN` 不再随每次请求发送；`adminData` 返回有效期8小时的 HMAC 签名会话令牌，浏览器仅在当前页面内存中保存。会话到期后需重新登录。部署或轮换口令后可在项目根目录运行 `pnpm admin:verify:cloud`，脚本只输出会话有效期和各集合记录数量，不输出长期口令、短期令牌或业务数据。

发布操作要求系统验证通过、人工审核通过，并至少有一个 `valid` 的官方来源。满足门槛的记录会与管理状态在同一事务内写入 `event_edition_public_cache`；下架时同一事务删除缓存。公开读取使用 `publicData`，应用函数权限规则后可运行 `pnpm public:verify:cloud` 验证只读契约。

“审核发布”页面的“运行 Kimi 审核”会由 `adminData` 云函数读取赛事来源：普通网页提取正文，图片链接直接作为视觉输入。返回的结构化建议会写入赛事 `aiReview` 字段及操作日志，但不会自动把来源设为有效、不会代替人工审核，也不会自动发布。

命令行自查：`pnpm admin:verify:cloud` 会附带回报云端 AI 配置、`blockers` 和最近一次自动检测运行记录；加 `--ai-check` 会真实跑一次 Kimi 审核验证端到端链路（消耗额度，只读赛事不写回数据）。部署云函数可用微信开发者工具 CLI：`cli cloud functions deploy --env <envId> --names adminData --project apps/miniprogram -r`。

自动检测的节奏由 60 秒函数超时决定，不能调大（微信云开发平台硬上限）。实测数据：

| 配置 | 单条耗时 | 结果 |
|---|---|---|
| 无输出上限、3 条并发 | > 40 秒 | 3 条里 2 条超时 |
| 无输出上限、单条 | 50~53 秒 | 贴着上限，不稳定 |
| `max_tokens` 封顶 + 要求精简 | **22 秒** | 稳定通过 |

结论：耗时主要来自输出生成，不是输入长度；而且 Kimi 端并发请求是排队的，**并发只会让每条都逼近上限**。因此定时器每 5 分钟触发一次，每次只处理 1 条「距上次审核超过 7 天」的赛事（`AI_REVIEW_CONCURRENCY` 可调但不建议大于 1），模型超时 50 秒、`max_tokens` 2000，并要求精简结论。手动审核用同样的上限但允许更长结论（`max_tokens` 2600）；后台「检测全部」也改成逐条串行，原因相同。

跑不完的留给下一次触发。运行日志写在 `admin_state/ai_review_runs` 文档里（保留最近 20 次），**不是独立集合**——云开发的集合必须先手动创建，写一个不存在的集合会静默失败，那样错误上报等于没有。`status` 区分 `completed`（已追平）、`partial`（还有剩余）、`idle`（无到期记录）和 `failed`。

连续失败的赛事会写入 `aiReviewFailure`（失败次数、时间、原因）并按 `失败次数 × 6 小时` 退避，最长一周，成功后自动清除。**没有这个退避，一条永远跑不完的赛事会每 5 分钟重试一次，无限消耗模型额度。**

云函数接受**任何** `Type === 'Timer'` 事件（不按触发器名过滤），因为 `adminData` 只有这一个定时任务；按名字精确匹配会让改名或手工新建的触发器被静默丢弃。运行日志的 `trigger` 字段记录事件的真实触发器名（`manual` 表示通过 `runScheduledAiReview` 手动调用），据此可判断哪些触发器实际存在。

## 来源抓取策略

AI 审核会抓取赛事记录中登记的官方来源（最多 3 个）供模型核对。抓取遵循以下约定：

- **抓取前检查 `robots.txt`**（`robots.js`，按标准分组解析、最长匹配优先、具名 UA 优先于 `*`）。被禁止的来源标记为 `blocked_by_robots` 并跳过，不会抓取。取不到 `robots.txt` 时按通行惯例视为允许。
- **User-Agent 诚实标识**为 `competition-review/1.0 (+admin source verification; ...)`，不伪装成浏览器，便于站方识别与联系。
- **量极小**：单次审核最多 3 个页面，定时任务每 5 分钟最多一条赛事。
- **审核结果记录 `evidence_status`**，逐条列出每个来源的抓取状态和读到的字符数，用于事后核对模型结论是否真有证据支撑。

已核查的 39 个来源域名中，**没有任何链接被 `robots.txt` 禁止**（64 个链接全部允许，20 个域名无 `robots.txt`）。

**关于拒绝 AI 爬虫的站点**：部分主办方站点（如挑战杯官网）在 `robots.txt` 中点名禁止 `GPTBot`、`ClaudeBot`、`anthropic-ai` 等 AI 爬虫，同时对 `User-agent: *` 只禁止少数后台路径。本项目的抓取器不属于这些具名爬虫，按字面规则落在 `*` 组，因此允许抓取其公开页面。**已决定按 robots.txt 的字面规则执行**：站方既然区分了具名 AI 爬虫与通用爬虫，该区分视为有意；且本流程的用途是协助管理员核对该主办方自身赛事信息的准确性。若后续需要更保守的策略，可改为「抓取但不送模型、仅供人工查阅」。

## 未决问题：定时触发器从未生效

**状态**：未解决。已确认**不是代码问题**，原因在云开发控制台／开发者工具一侧。

**当前影响**：自动定时 AI 审核不可用，需人工在审核发布页点「检测全部」。当前 30 场赛事规模下可接受（逐条约 22 秒，全量约 10 分钟）。

**何时必须解决**：赛事数量增长到人工批量检测不现实时；或上线真实用户后提醒推送必须可靠时（见下方连带风险）。

### 已排除的原因

| 假设 | 排除依据 |
|---|---|
| 触发器名不匹配 | 云函数已改为接受任意 Timer 事件，仍无事件到达 |
| cron 增量写法不合规 | `0 */5 * * * * *` 与官方文档写法 `0 0/5 * * * * *` 均试过，无差异 |
| 函数超时导致写不下日志 | 手动调用 22 秒完成，运行日志正常落盘 |
| 运行日志写入失败 | 日志已从不存在的 `ai_review_runs` 集合改写入 `admin_state`，已验证可读回 |

**结论**：在 cron 周期为 5 分钟的情况下连续观察 7 分钟以上，零 Timer 事件到达。

**关键证据**：在开发者工具中对 `config.json` 执行「上传触发器」，**工具提示为绿色即报告注册成功**，但随后 `adminData` 与 `sendReminders` 两个函数在 7 分钟内仍然零调用。即上传操作本身不报错、看似成功，触发器却从不执行。

配置、cron 写法、触发器名、上传方式均已逐一排除，**判定为环境级限制**：该云开发环境（**体验版**）中定时触发器不实际运行。腾讯云计费文档提到触发器能力处于内测阶段，与此现象一致。

### 🔴 已确认：sendReminders 同样从未被触发，提醒推送功能不工作

`sendReminders` 已用同样方法验证：在 `exports.main` 的守卫**之前**加入 `logInvocation` 探针（写入 `admin_state/reminder_runs`，记录 `eventType`、`triggerName`、是否被守卫拒绝），部署后在 cron 周期为 5 分钟的情况下连续观察 7 分钟——**零次调用**，探针记录始终为 `null`。

其触发器名 `send-reminders-every-5-minutes` 在 `config.json` 与 `reminderDelivery.js` 的 `EXPECTED_TRIGGER` 中完全一致，不存在名称不匹配问题。

**因此这不是单个功能的配置问题，而是环境级故障：该云开发环境中没有任何定时触发器注册成功。** 两个互相独立的云函数均从未收到过 Timer 事件。

**用户侧影响**：

- 用户保存的提醒永远不会推送
- `recoverTimedOutClaims` 从未执行，`delivery_status` 卡在 `queued` 的记录会永久卡住
- 全程无报错、无日志，故障不可感知

**上线前必须解决。** 提醒推送是用户可感知的核心功能，AI 审核尚可人工触发，此项无替代方案。

探针代码保留在 `sendReminders/index.js` 中（单次覆盖写，不读历史，适配其 3 秒超时），可随时用 `pnpm admin:verify:cloud` 查看 `lastReminderInvocation` 字段确认触发器是否恢复。

### 另一个独立隐患：sendReminders 超时仅 3 秒

云端实测 `sendReminders` 的 `timeout` 为 3 秒（`adminData` 已调至 60 秒）。`docs/reminders.md` 明确要求「若要把 `REMINDER_BATCH_SIZE` 提高到 50，超时应先配置为至少 30 秒」。当前未配置该环境变量、默认每批 1 条，尚可运行；**但在触发器修复后、调大批次前，必须先把超时调上去**，否则会批量超时且同样无声失败。

不确定云端是否配好时，也可点“审核发布”页工具栏的“检查 AI 配置”。它调用 `adminData` 的 `aiReviewConfig`，回报密钥是否存在、密钥长度、是否误带引号或空格、当前模型与地址、云函数 Node 版本和 `fetch` 可用性。**该接口只回报密钥是否存在和长度，不会回传密钥内容。**

赛事、纠错和 AI 任务状态都带独立版本号。后台保存时必须携带启动数据返回的版本，并在云数据库事务内核对；缺少版本的旧客户端会被拒绝。若另一个页面已经先保存，当前写入会被拒绝并提示刷新，避免整组数据被旧页面静默覆盖。需要在线验证此保护时，可在 `apps/admin` 下运行 `node scripts/verify-admin-cloud.mjs --write-check`；该检查会用当前赛事记录做一次同值写入，再确认旧版本请求被拒绝，只会推进状态版本和更新时间，不会改变赛事内容。

## 安全边界

- 不要把 `ADMIN_TOKEN` 改成 `VITE_ADMIN_TOKEN`，`VITE_` 变量会进入前端构建产物。
- 不要把 `.admin-token.local` 上传到 Git；仓库已通过 `*.local` 忽略该文件。
- `audit_log` 由 `adminData` 云函数写入，前端不直接写数据库。
- 正式上线前应定期轮换管理员口令。
