# 管理后台任务与反馈模块

赛事筛选、入库、发布及清洗验收以 [大学生专业赛事数据质量 SLA](data-quality-sla.md) 为准；其中明确区分验收目标和当前已实现能力。

## 纠错审核

纠错采用AI预审优先的两级流程：`pending_ai_review → ai_queued → ai_passed/ai_flagged`。AI认为证据不足、来源冲突、信息过期或存在高风险时进入“问题待人工审核”；AI低风险通过结果进入“AI通过抽查池”。管理员可以定期标记“抽查正确”或“抽查有误”，后台持续计算抽查正确率。抽查有误会把纠错重新放入问题列表，并把对应AI任务转为人工处理。

人工问题按 `human_reviewing → accepted/rejected` 流转。管理员必须填写审核说明；采纳后，关联赛事届次自动转为 `reviewing`，人工审核回到 `pending`，并增加 `user_feedback_requires_review` 质量问题，避免未经复核直接发布。AI排队、人工审核和抽查动作都写入 `audit_log`。

真实用户提交从 `feedback` 集合进入后台。后台保存时只把本次发生变化的用户纠错按每批20条同步回规范集合；Mock 验收样本仍只保存在 `admin_state`，不会伪装成真实用户提交。用户纠错接口对每个云端账号采用24小时滚动窗口，最多接收20条。

没有真实AI Provider时只能创建 `feedback_review` 排队任务，不能在客户端生成或伪造审核结论。服务端AI结果必须满足 `feedback_ai_review_result.schema.json`，保留模型、Provider、提示词版本和证据引用，供后续抽查追责。

## AI失败任务

失败任务保留任务类型、赛事届次、Provider、模型、错误码、错误信息、重试次数和下一次重试时间。后台“重试”只把任务放入队列，不直接标记成功；达到最大次数后转人工。正式任务处理器必须使用锁或条件更新抢占任务，防止重复执行，不记录密钥或完整敏感请求。

## 操作记录

赛事编辑、恢复种子数据、纠错采纳/驳回、AI任务重试/转人工/关闭统一写入操作记录。记录至少包括管理员、动作、对象类型、对象ID、变更字段和时间。正式环境的 `audit_log` 只允许服务端写入，不允许管理员客户端修改或删除。

## 当前开发模式

三项功能使用浏览器本地存储，并带有明确的 Mock 纠错和失败任务样本。它们用于验收界面、状态机和审计联动，不代表真实用户提交或真实AI调用结果。接入 CloudBase 后应由管理 API 替换本地仓库。
# Jev 抓取前置筛选

每日发现流水线在判重后使用 Jev Decisions API（`typesafe/jev-1.13`）对搜索结果批量分类。明确的目录、校赛、获奖报道和栏目由代码规则先处理；当届赛事官网、承办方正式通知、官方报名入口继续抓取。低置信度结果写入 `runs/<日期>/jev-filter-report.json`，供人工复查。

详情页的报名、章程、指南和组织机构链接再由 Jev 排序；抓取器最多跟进 3 个高价值 HTML 页面，保留原网址、最终跳转地址及抓取状态。抓取遵守 robots.txt 和站点限速。Jev 分类只影响抓取优先级；赛事是否进入库仍由现有的身份、范围、字段和时间规则决定，通知标题不可作为赛事名称入库。

本地运行从项目根目录 `.env` 读取 `OPENROUTER_API_KEY`。服务器运行可将密钥单独放在 `/opt/daily-contest/.openrouter-key`（文件内容只有密钥，权限 `600`），或为 systemd 服务设置同名环境变量。没有密钥或 Jev 请求失败时，候选继续走原来的详情抓取与确定性验收。运行日志记录分类、费用和调用故障，不记录密钥。
